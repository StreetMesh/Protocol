# Conformance

Executable vectors for the parts of StreetMesh that two independent servers must
agree on byte for byte.

Unfamiliar terms are defined in [the glossary](../GLOSSARY.md).

```sh
node runners/verify.mjs
```

## What conformance is for

A federated protocol is a promise that two programs, written by people who have
never met, in languages that share nothing, will understand each other exactly.
Prose cannot carry that promise on its own. Prose can say "the document is
signed"; it cannot say which bytes, in which order, with which encoding of an
empty field.

The gap between those two sentences is where interoperability failures live, and
they have a characteristic shape: **silent, data-dependent, and mutually
invisible.** Two servers each behave correctly by their own reading. Most
messages pass. Some fail, and which ones depends on what happens to be inside
them. Each side's logs show the other misbehaving.

Vectors close the gap by making the wire testable rather than describable. A
conforming implementation is one that reproduces every file in this directory —
not one whose author believes it follows the specification.

**So: a claim about the wire that is not in this directory is an opinion.** These
files are the arbiter.

## Who this is for

Anyone implementing StreetMesh — a server, a client, a library, in any language.

The vectors are plain JSON with no framework, no toolchain and no dependency on
any particular implementation, so proving conformance never requires reading
somebody else's source. That is the point of their being data rather than a test
suite: a test suite in one language is an argument for that language.

## What is covered

| File | Pins |
|---|---|
| `encoding/dag-cbor.json` | Deterministic CBOR, including the map key ordering that determines every `did:plc` |
| `encoding/multikey.json` | Public keys as multibase multicodec, on all three curves in use |
| `identity/did-plc.json` | Deriving a `did:plc` from its genesis operation |
| `identity/key-history.json` | Which key an identity was using at a given moment |
| `encoding/tid.json` | Record keys, and that sorting them sorts time |
| `encoding/cid.json` | Content addressing — naming a record by hashing it |
| `signing/jws.json` | Compact JWS with `alg` EdDSA |

Coverage grows with the protocol. Anything two servers must agree on belongs
here; anything an implementation is free to decide for itself does not.

## Why the vectors can be trusted

Vectors generated by an implementation and then used to test that same
implementation prove nothing. Two things break that circle.

**The identity vectors are drawn from the live network.** `identity/did-plc.json`
holds genuine genesis operations of real ATProtocol accounts alongside the DIDs
the network already assigned them. Reproducing those is agreement with a running
system rather than with an author's intent — and because a `did:plc` is the hash
of a DAG-CBOR encoding, they transitively pin the encoding as well.

**The runner is a second implementation.** `runners/verify.mjs` is written in a
different language on a different cryptographic stack from the one that produced
the vectors, from the specifications rather than by translation, sharing no code
with the generator. It also re-signs the JWS vector from its claims and checks it
lands on the same string, so the format is fixed by the specification rather than
by one language's habits.

If the runner and the vectors ever disagree, at least one is wrong and neither
gets the benefit of the doubt.

## Verifying something older than the key that is published now

A DID document publishes the key that is current. That is the wrong question to
ask of a signature made earlier, and asking it is a silent way to lose history.

Keys are rotated — after a compromise, on moving to another server, or as
ordinary hygiene. A signature checked against today's key fails for a document
that was perfectly good when it was made, and the failure looks identical to
forgery. This is not hypothetical: identities on the live network have rotated,
and nothing they signed beforehand verifies against what their document
publishes today.

**So a verifier resolves the key that was current when the document was signed,
not the key that is current now.** `did:plc` makes this answerable because its
audit log is retained and timestamped; `did:web` cannot answer it at all, since
it publishes a document and no history.

Two rules, both pinned by `identity/key-history.json`:

- A period runs `[from, until)`. The instant of a rotation belongs to the new
  key.
- Outside an identity's lifetime there is no answer, and an implementation must
  refuse rather than fall back to the earliest key. Falling back would validate
  anything backdated to before the identity existed.

### Choosing the moment

Which moment to resolve against is a decision with security consequences, and
implementations should make it deliberately.

A timestamp inside the signed document is asserted by whoever signed it. It says
when they *claim* to have signed, which is sufficient against ordinary rotation
and worth nothing against somebody holding a retired key — they can simply
backdate. An anchor asserted by the receiving party at the moment of receipt is
much stronger, because the signer does not control it.

This is an argument for recording when a document arrived rather than trusting
when it says it was issued.

## The two rules most often got wrong

**DAG-CBOR map keys sort by length first, then bytewise.** This is RFC 7049's
canonical order, not the plain lexicographic order RFC 8949 later adopted and
which most general-purpose CBOR libraries produce by default. Reversed, every DID
an implementation computes is wrong, and the failure surfaces as an
unverifiable signature rather than as an encoding error.

**A signed document is verified exactly as received.** No trimming, no coercion
of empty values, no reordering, no re-serialization. Signatures cover bytes, so
any normalization between the wire and the verifier is corruption — including
normalization a web framework applies before application code ever runs, which is
a common default. `signing/jws.json` therefore contains a record with a blank
string field: an implementation that tidies its input cannot reproduce it.

## Versioning

Implementations should pin a revision of this repository rather than track its
default branch. Pinning keeps "which version of the protocol does this
implement" an answerable question, and makes adopting a protocol change a
deliberate act with its own commit.

**A change to a vector is a change to the protocol.** Vectors are generated from
a reference implementation and cross-checked by the independent runner, but they
are not regenerated as a matter of routine — a vector that shifts because an
implementation shifted is that implementation announcing a breaking change, and
should be read as one.

## Adding a vector

Worth adding when it pins something two implementations could reasonably read
differently: an encoding boundary, an empty or absent value, a sort order, a
length prefix that crosses a size threshold, a signature format detail.

Not worth adding when it tests an implementation's internals, restates something
already pinned, or asserts behavior an implementation is free to choose.

Every vector must pass `runners/verify.mjs` before it lands, since a vector the
independent runner cannot reproduce is a bug in one of the two.
